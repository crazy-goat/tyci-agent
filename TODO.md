# tyci — backlog

Working agreement: one item at a time. A Sonnet subagent implements, an Opus
subagent reviews, the Sonnet subagent fixes what the review found, and that
loop repeats until the review comes back clean. Then the next item.

The loop runs without asking which item comes next: pick one, implement, review, fix, merge, push, report. Only stop to ask when a decision is genuinely the owner's — a semantic choice, a trade-off with no obviously right answer, or something that changes what gets built. Ordering is not one of those.

Status: `todo` · `wip` · `review` · `done`

Work happens in a git worktree, never in the main checkout. A coder subagent
gets `isolation: "worktree"`, the review runs against that worktree, and only a
feature that came back clean is merged into `main`. The reason is not tidiness:
the main checkout is where the person reads code and thinks about what to build
next, and a tree carrying three half-finished features is unreadable for that.
`main` therefore stays committed and clean between items. **Every closed step ends with a push**: merge the clean branch into `main`, run the full suite there, `git push origin main`, then remove the worktree and delete its branch. Nothing finished is allowed to exist only on this machine — that is how a session's work was nearly lost once already, sitting on an unpushed worktree branch that a cleanup would have deleted.

The loop feeds itself. Anyone working an item — coder or reviewer — who trips
over a real problem outside their scope does NOT fix it and does NOT stay quiet
about it: it goes in the Inbox below, one line, with a file:line and why it
matters. Fixing it inline would smuggle unreviewed work into an unrelated diff;
dropping it means finding it again in three weeks. Between rounds the inbox is
triaged — promoted into the tables with a size, merged into an existing item, or
struck out with a reason. The queue is expected to grow faster than it drains at
first; that is the point, not a failure.

| 51 | **Styled markdown while the text is still streaming.** Today markdown is glamour-rendered exactly once, when a block finishes (`forceRenderDirtyBlocks`, `display/tui_markdown.go:111`); during the stream the user reads raw, unstyled text re-wrapped one line at a time by `streamWrap` (`display/tui_render_block.go:9-63`), with transport-level coalescing at 33/100 ms (`display/tui_api.go:183`). That is cheap and correct, but a long answer is read *as it arrives*, and reading unstyled markdown for thirty seconds is the actual pain. Decided (owner, full variant): render the safe prefix progressively at blank-line boundaries and keep the tail raw. **The safe-boundary rule is one sentence: a `\n\n` is a safe flush point iff no fenced code block is open there.** Tables need no state at all — a GFM row is a single line and a table ends at the first non-row line, which a blank line always is, so by the time we see `\n\n` the table is already over; a lone `|` line with no delimiter row was never a table. Fences are the only construct that genuinely spans blank lines with no single-line terminator, so track them: marker char (`` ` `` vs `~`), opening run length (a fence closes only on a run **≥** its opening, so a 3-backtick line inside a 5-backtick fence must not close it), and indent 0-3. Indented 4-space code blocks are symmetric to fences and deliberately **out of scope** per the owner's narrowing — worst case one block flushes as two for a few hundred ms. Setext headings cannot straddle a boundary (CommonMark forbids a blank line between text and underline), and front matter does not occur mid-reply. **Why mid-stream imperfection is acceptable: the whole-content render at block finish already exists, so every artifact is self-healing** — this is what removes the correctness objection to the whole idea. Scan is incremental (`O(new bytes)`, anchored on the last `\n` exactly as `streamWrap` already does at `display/tui_render_block.go:37`), never re-scanning history; each byte reaches glamour at most once because segments partition the content, so this must not reintroduce the O(n²)-per-token pathology `appendOrAppend`'s comment warns about (`display/tui_blocks.go:276-320`, issue #84). New per-block state (`inFence`/`fenceMarker`/`fenceLen`/`fenceIndent`/`safeUpto`/`renderedUpto`/`renderedPrefixLines`) keyed by block index next to `streamWraps`, with the **same lifecycle at every site that clears `streamWraps`** (`tui_blocks.go:192`, `tui_scroll.go:92`, `tui_scrollback.go:273`, and the deletes in `tui_markdown.go:142,164,177,180`) — a missed clear site is the likely first bug. `streamWrap` must be rebased to wrap `content[renderedUpto:]` rather than byte 0.
