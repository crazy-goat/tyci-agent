# tyci — backlog

Working agreement: one item at a time. A Sonnet subagent implements, an Opus
subagent reviews, the Sonnet subagent fixes what the review found, and that
loop repeats until the review comes back clean. Then the next item.

The loop runs without asking which item comes next: pick one, implement, review, fix, merge, push, report. Only stop to ask when a decision is genuinely the owner's — a semantic choice, a trade-off with no obviously right answer, or something that changes what gets built. Ordering is not one of those.

Status: `todo` · `wip` · `review` · `done`

Work happens in a git worktree, never in the main checkout. A coder subagent
gets `isolation: "worktree"`, the review runs against that worktree, and only a
feature that came back clean is merged into `main`. The reason is not tidiness:
the main checkout is where the person reads code and thinks about what to build
next, and a tree carrying three half-finished features is unreadable for that.
`main` therefore stays committed and clean between items. **Every closed step ends with a push**: merge the clean branch into `main`, run the full suite there, `git push origin main`, then remove the worktree and delete its branch. Nothing finished is allowed to exist only on this machine — that is how a session's work was nearly lost once already, sitting on an unpushed worktree branch that a cleanup would have deleted.

The loop feeds itself. Anyone working an item — coder or reviewer — who trips
over a real problem outside their scope does NOT fix it and does NOT stay quiet
about it: it goes in the Inbox below, one line, with a file:line and why it
matters. Fixing it inline would smuggle unreviewed work into an unrelated diff;
dropping it means finding it again in three weeks. Between rounds the inbox is
triaged — promoted into the tables with a size, merged into an existing item, or
struck out with a reason. The queue is expected to grow faster than it drains at
first; that is the point, not a failure.

| 10 | No history compaction and no context-budget accounting. The session format already has a `compaction` event and `session.WriteCompaction`, and replay applies it — nothing ever writes one. Needs `/compact` (with optional focus instructions) and an auto-compact threshold. **Also a model-facing `compact` tool plus a budget reminder** — the model compacts itself instead of waiting for the user, since quality visibly degrades past ~100k tokens while cost keeps climbing. Design points settled in a side-conversation: **(a) compaction is a view over the log, never a deletion** — the raw JSONL stays and the event only says "read the summary from here", so a bad choice by the model loses nothing; `sanitizeMessageSequence` (`session/session.go:565`) is already called by the compaction replay path, so a cut landing inside a tool-call/result pair is handled. **(b) The reminder must state a fact, not a diagnosis** — "you are at 120k of 200k" rather than "your thinking is degrading". The model at 100k is the worst available judge of its own degradation, and a panic instruction produces a panicked summary; a number it can act on does not. **(c) Reminders fire only at turn boundaries** — `agent/agent.go:290-322` injects them when the model believes it is finished (`!more && !drained`), with a per-turn cap. That is the right moment for compaction (no half-finished tool loop) but it will not interrupt one long turn; wanting mid-turn reaction is different machinery. **(d) Let the model persist what matters before compacting** — to `memory/` or a file — so the summary is not the only surviving artefact. **(e) Every compaction writes a full markdown dump of the session and hands the model its path** — "if you need it, the whole record of what you did is here". So the flow is: the model persists what matters (memory or a file), compaction writes the dump, and the model comes back holding a path rather than only a summary. **The dumps exist to be searched, not read** — `grep`/`rg` over the session directory is the primary interface, which constrains the format more than prettiness does: **never soft-wrap** (a wrapped line splits a path or identifier in half and grep stops finding it); make **every line self-identifying** with a short stable prefix (e.g. `[12] [bash]`) so a hit tells you where it came from without jumping around the file; write **paths, tool names and error text verbatim** rather than paraphrased, since those are exactly the search terms; **strip ANSI escapes**, or `grep error` misses lines whose text is interleaved with colour codes; and include tool inputs and outputs (under a size cap) because "which file did I edit" and "what was that error" are the questions actually asked. Since there are many files, `rg` across the directory is the normal usage, so filenames should be meaningful rather than bare hashes. **One markdown file per session, not one nested document** — decided, and it removes most of the machinery: no recursion, no `seen` map guarding cycles, no heading-level arithmetic. The main session's file carries a line per child linking to that child's own file; links are relative and every file lives in the same session directory, so the directory can be copied or zipped and the links still resolve. A child's file is written when the child finishes rather than re-derived at compaction time, and a long session no longer produces one enormous document — you open only the child you care about. This dovetails with item 16: the path to a child's markdown is a natural part of the "here is how to come back to me" line. Two decisions taken up front: the dump lives **beside the session JSONL** (`session.SessionDir`) as a sibling file, so it is found with the session and discarded with it rather than starting a second store; and the dump is a **derived artefact, never a second source of truth** — it is regenerated from the JSONL, so compaction can never be an unrecoverable operation. Reuse the decoding path `session show` already uses (fixed in item 12) instead of writing a third parser. The same renderer gives `tyci session export --markdown` for free, which is useful on its own. | 21 | **Grandchildren — a crippled "scout" that may nest to depth 4.** Decided: full recursion is not wanted, but depth 3-4 is. That is safe for a scout and unsafe for a `subagent`, so the two get different limits: **depth 1 stays the full `subagent`** (jobs, async, worktree, named agents), and **depth 2 through 4 may only spawn scouts**, which nest freely inside that range. Depth alone is not the safety property — a scout is safe at depth 4 for the same reasons it is safe at depth 2: it registers no job, so the flat notice/answer channel, `PendingLines` and the 50-job retention never see it; it is synchronous and cannot detach, so it dies with its caller; and it **inherits its caller's remaining deadline**, so a chain converges on its own instead of nesting 180s inside 180s inside 600s. What actually bounds the burn at depth 4 is the concurrency semaphore and the per-turn budget below, not the depth number. Do NOT lift `subagentDeniedTools`. A general `subagent` at depth 2 breaks the notice/answer model in user-visible ways, and buys little over flat fan-out. Instead add a separate tool with a deliberately narrow profile: `scout` — one task string, synchronous, read-only tools (`read, grep, glob, ls, bash` read-only, `help, lua`), `MaxIterations` 15 (not the unlimited default), 180s **inheriting the child's remaining deadline**, no `async`, no `isolation`, no `agent`/`model` choice, and no job of its own.
